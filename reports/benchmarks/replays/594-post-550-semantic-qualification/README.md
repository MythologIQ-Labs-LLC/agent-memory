### A1: timestamp semantics (`source-anchor-manifest.json`, `source-timestamp-audit.json`)

Source: `xiaowu0162/longmemeval-cleaned` @ `98d7416c24c778c2fee6e6f3006e7a073259d48f`, `longmemeval_s_cleaned.json`, sha256 `d6f21ea9…a442`. The source file is not committed.

| field | scope | generated by | maps to `observed_at`? |
| --- | --- | --- | --- |
| `haystack_dates[i]` (`YYYY/MM/DD (Ddd) HH:MM`) | one per session | upstream history compiler: the simulated time the session occurred | **yes**, session-level anchor for every user turn of that session |
| `question_date` | one per question | upstream compiler | no: this is the time of asking, not an observation. P2 uses it only as the recall `reference_time` |
| message `role`, `content`, `has_answer` | message | upstream | no: messages carry **no** timestamp, and `has_answer` is gold |
| `answer`, `answer_session_ids`, the `answer_` id prefix | gold | upstream | no: never reaches Agent Memory |

The upstream README (`9e0b455f`) describes `haystack_dates` as "the timestamps of the history sessions" and tells users to "feed the timestamped history to your own chat system". The generator, `data/custom_history/sample_haystack_and_timestamp.py` (sha256 `a2105d0d…30f4`), builds these dates as follows:

* evidence-session dates come from the question's designed timeline;
* filler dates are sampled around them;
* every date gets a random time of day.

The dates are therefore **defensible as a session-level observation anchor**. They are input metadata offered to every system, not a label to be predicted. Caveats:

* they are synthetic;
* they give no message resolution;
* they carry no time zone, so they are declared as UTC by convention;
* within-day list order is random, so 211 questions are not in chronological list order.

Source checks: all 23,867 dates parse, with 0 day-of-week mismatches and 0 message-level timestamps. 76 questions have sessions dated after `question_date`, including 66 gold sessions; this is an artifact of the upstream compiler.

### Why nothing moved (`null-mechanism-audit-9fc452f.json.gz`)

A ranking change requires a query whose intent orders temporally. That is 40 of the 500 questions (current 30, prospective 10, all inferred at high confidence). The audit re-ran all 40 on both planes under C, P1, and P2 and recorded the runtime's own `ordered_before_next_by` stage for every adjacent top-50 pair.

**Interpreted self-validity demotion: 0 rows, EVIDENCE GAP.**

* Only 1 of those 40 questions admits a memory with a resolved window, on the turn plane: `1cea1afa`, "How many Instagram followers do I currently have?".
* That memory is a non-gold turn at rank 132, with window 2023-05-27 to 2023-08-27.
  * **P1:** it is labelled `no_reference_time`.
  * **P2:** the reference is 2023-06-14, inside the window. The window would *affirm* applicability, which interpreted validity may never do, so it stays `unknown_temporal_basis`.
* Across all 40 questions and all three profiles, 0 admitted candidates carry basis `interpreted`.

**Declared observation-clock tie-break: 0 metric-visible changes.**

* On the turn plane, 27 of 40 full rankings do differ from C, but the earliest difference is at **rank 65**, below the deepest metric (@50). Gold ranks do not change at any depth. On the session plane all 40 are identical at every depth. The other 460 questions have no ordering intent, so no clock enters their order.

### LongMemEval_M

**Not warranted.**

* P1, the primary profile, is structurally inert at any scale: without a recall reference instant, no interpreted window can demote.
* P2 could only demote filler memories whose window excludes the question date. Resolved windows occur in about 0.03% of turns, so M's extra filler would add a few such candidates to at most the 40 ordering-intent questions.
* This is not a hypothesis that S cannot characterize. S already shows that the mechanism's inputs are scarce and that its behavior on the one reachable case is correct.
