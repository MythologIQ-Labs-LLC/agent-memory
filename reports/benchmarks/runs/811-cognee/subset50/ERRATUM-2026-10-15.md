# Erratum: Cognee 50-question preregistration names the wrong backend (#811)

**Recorded 2026-10-15 by the external-execution session. The original files in this directory are
left byte-for-byte unchanged.** This erratum responds to the finding in
[#811](https://github.com/MythologIQ-Labs-LLC/agent-memory/issues/811#issuecomment-6192667723).

## What is wrong

`preregistration.json` (sha256 `ede9ec1c681e4dd5911570b92b4a2c06b8b49f6a8f19b54c0bfaa6ca442d9dd5`)
declares `backend: "jev_mem_laya"` and
`external_backend: ["longmemeval_jev_mem_bridge:install_longmemeval_jev_mem_backend"]`.
It is **byte-identical** to `../../817-jev-mem/subset50/preregistration.json`: same sha256, same
`registered_at` (`2026-10-15T04:37:40Z`). That Jev-Mem file was committed in `865f5df` at
04:37:51Z. This Cognee file first appears in git in `66cc07f` at 08:46:37Z, in the same commit as
the first Cognee rows; the first Cognee row finished at 06:48:13Z. So **no Cognee-specific
preregistration is evidenced before Cognee executed**. The file was copied from Jev-Mem's.

The resumable driver checks an existing preregistration only for matching `question_ids` and
input sha256, not backend identity. That is why the copy did not stop the run.

Two further qualification gaps, found while preparing the rerun:

- **Unpinned models.** Cognee downloads its GLiNER extractor and embedding model on first use.
  The original run recorded neither repository revisions nor file hashes for them.
- **No system identity.** `session.cognee_gliner_local.summary.json` has `external_system: null`.

## What is correct

- The input (`longmemeval_s_cleaned.json`, sha256 `d6f21ea9…a3442`) and the selection (seed
  `agent-memory-longmemeval-subset-v1`, 50 ids, ID-list sha256 `5266568e…7339`) are correct.
- The 15 rows in `session.cognee_gliner_local.rows.jsonl` (sha256 `7bdd80a0…04e8b`) are Cognee's.
  They carry only Cognee fields (`remember_status`, `returned_entry_kinds`), none of Jev-Mem's
  (`laya_*`, `jev_*`, `system_*`). Every row has `llm_calls: 0` and returns only `CHUNKS:chunk`
  entries. The rows follow the preregistered selection in order. They have 0 runtime failures.
