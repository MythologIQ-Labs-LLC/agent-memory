## 2. Hunk-by-hunk findings

### H1 adapter 35-45: `DERIVATION_KEY = "canonical_derivation"`, `DERIVATION_POLICY`

Changes: two module constants. Readers of `attributes[DERIVATION_KEY]`: only `_derivation_refs` (806). Writers: only `_write` (749).

Attack: attribute injection through the public surface. **None exists.** `_write` (740-749) builds `attributes` from scratch (`{DECLARED_TEMPORAL_KEY: ...}` then provenance, semantics, derivation); no proposal field, facade keyword, `overrides` entry or envelope field flows into `attributes` (`PUBLIC_PROPOSAL_FIELDS` contract.py 50-62 has no `attributes`; the facade `_proposal` 645-717 never touches attributes). The only other `write_fact` callers in non-test code are harness modules (`harness/benchmark_security.py:50`, `harness/forbidden_hits.py:248`). A writer cannot forge `canonical_derivation` to bind a foreign fact or unbind its own through any public path. The attribute is set at 749, after every other attribute, inside the same call that writes the row; nothing merges caller data afterwards.

Is the recorded `bound` list itself served to readers? `write_semantics` (984-989) serves only `attributes[WRITE_SEMANTICS_KEY]`; no public projection reads `fact.attributes` (grep: `.attributes` outside the adapter is read only by `sqlite_substrate` persistence and `run_644_v7_replays.py`). The bound list reaches: SQLite `facts.attributes_json`, the file checkpoint export (`substrate.py:282 asdict`), `sqlite_substrate.py:1036/1077` (reachability/merkle rows), and the canonical-json qualification scripts. Those are operator/host surfaces, not caller projections. Had the list been served, it would have told a co-holder of the citing fact which cited strings are real in-tenant facts the writer could read; it is not served. **NOTE (no action).**

### H2 adapter 748-749: `attributes[DERIVATION_KEY] = {"policy": ..., "bound": list(self._bound_derivation(proposal))}`

Changes: the derivation is decided inside `_write`, after `_interpret_write`, before `write_fact` (750) and before `_fact_scope[uuid] = scope` (761).

Time-of-check/time-of-use: `_bound_derivation` and `write_fact` run in the same synchronous call under the facade's `_serialized`; no interleaving point exists between them in this runtime. The uuid is minted at 741 before binding, so a writer who predicts its own next sequential id and cites it finds it absent from `_fact_scope` and it stays unbound (correct: a fact cannot depend on itself).

Correction and supersession: `commit_proposal` runs `_supersede_current` (529) and then `_write` (542); the replacement fact gets its own `_bound_derivation` under the correcting writer's context, and the invalidated predecessor keeps whatever record it had. The replacement record (`_record_replacement`) and the rejected-value row (683-688) keep the correction's `evidence_refs` verbatim; both reach readers only through facade `history` (`rejected_values`, scrubbed with the reader-aware predicate, 1285-1289). This is the right behaviour under the ruling.

**SHOULD FIX (minor, robustness) SF-2:** `_bound_derivation` 793 does `dict.fromkeys(proposal.evidence_refs)` before the `isinstance(ref, str)` guard at 794. An unhashable evidence ref raises `TypeError` inside `_write`, i.e. after `_supersede_current` has already invalidated the current head and recorded the rejected value (529-541) but before the replacement is written and before `_current_fact_by_memory` is updated: the memory is left with an invalidated head that is still its "current" fact. ### H3 adapter 776-799: `_bound_derivation`

Changes: binds `ref` iff `ref in self._fact_scope` and `_domain_identity_refusal(ref, self._tenant, context) is None`, with `context = self._writer_context(proposal)`.

Writer context vs. the context the adapter judges the proposal under: `_writer_context` (316-320) is the same function `write_target_refusal` -> `fact_eligible_for_writer` (322-326) uses, and `writer_context` (304-314) derives `target_domain_refs` exactly as `_write_scope` (813-825) derives the new fact's `domain_refs` (`isolation_domain_refs or (scope,) or (tenant,)`). The facade's `_visible_head`/`_state_snapshot` (616-640) build the same context from the envelope with overrides applied (`_writer_context` 606-614), with `actor_id` protected from overrides (687-690). I found no path where the binding context and the judging context differ:
- `required_isolation_domain_refs` are not part of any `RecallContext`; they constrain *readers* of the new fact and are checked for the *cited* fact against the writer's target domains by `_scope_refusal` (1673-1674). Consistent with recall.
- `purpose` is carried but not gated anywhere; consistent with recall.
- `task_ref`/`project_ref` from overrides are in the context and are gated (1688-1694). `test_project_and_task_restrictions_decide_what_binds` pins it.
- Shared membership is evaluated against `proposal.actor_id` at commit (1680-1686): a member binds, a stranger does not, later revocation keeps the dependency, later grant binds nothing (pinned by the four `SharedDomainAndRestrictions` tests and `SharedDomainDurable`). This is the owner's commit-time boundary.
- Group id: `_bound_derivation` passes `self._tenant`; `fact_eligible_in_context` passes `fact.group_id`. They differ only for a foreign-tenant fact in a shared substrate (test-only configuration), and such a fact is never in this adapter's `_fact_scope`, so it is unbound either way.

Host-supplied scope: `overrides` can declare any `isolation_domain_refs`; the binding then follows the declared scope. This is the same privilege the recall context already grants (docs/44 "Scope is privileged host input"), so it adds no capability.

Deleted-but-readable source: `_fact_scope` survives pruning and permanent deletion (never popped; `restore_checkpoint_state` 402-410 restores it whole), so a deleted source the writer could read binds and the new fact is immediately `derived_from_tombstoned_source` (1432) / `derived_from_deleted_logical_memory` (2013) to its own writer. The writer could already learn that deletion through `history(M) -> tombstoned` (`public_deleted_version` 1943-1962 admits it), so no new disclosure. A purged *foreign* id and a never-written id differ only by a `dict` lookup at 794 (prior B.2 timing note; not re-argued).

Forward reference: `ref not in self._fact_scope` -> unbound, recorded, never revisited (`_derivation_refs` reads the record only). Matches the ruling. **No finding.**

### H4 adapter 801-809: `_derivation_refs` (legacy fallback)

Changes: returns `record["bound"]` when `attributes["canonical_derivation"]["bound"]` is a list/tuple, else `fact.episode_uuids`.

Callers: 976 (`_semantics_visible`), 1432 (`_admission_refusal`), 2013 (`_deleted_lineage_reason`), 2053 (`_derives_from_deleted` traversal), 2273 (`undeclared_residue`). Attack: make a legacy fact bind retroactively or strip a bound dependency.
- Runtime: facts are immutable; no code path rewrites `attributes` after `write_fact` (grep: no `replace(fact, attributes=...)`, no substrate attribute update API besides the whole-row `write_fact`). Correction writes a new row. Restore/export round-trips `attributes` unchanged (in-memory `substrate.py:282/330-333`, SQLite `_fact_from_row` 996-1010). No runtime migration of the key exists anywhere (repo grep for `canonical_derivation` hits only adapter.py, tests, docs, reports).
- Malformed record (tampered store, `bound` not a list): falls back to `episode_uuids`, i.e. toward *more* taint (tenant-wide), which protects deletion completeness but reopens F-R3-2 for that fact. Fail-closed in the deletion-completeness sense; acceptable.
- **Checkpoint migration (BLOCKING for the legacy-upgrade decision, SHOULD FIX for the code) SF-1:** `checkpoint_migration._validate_migration_state` protects `episode_uuids` and the other `protected_fact_fields` (713-721) and the governance maps (`_PROTECTED_ADAPTER_FIELDS` 148-161, including `fact_scope` and `tombstones`), but **not `attributes`**. A deterministic transformer applied through the governed migration path may therefore add, alter or delete `attributes["canonical_derivation"]` on any fact: it can bind a foreign reference retroactively (re-creating the F-R3-2 oracle for that fact's readers), bind a reference that did not exist at commit, or set `bound: []` to release a legitimate dependency from deletion completeness, all while the migration's own invariant text ("cannot alter fact authority/currentness field") passes. Before #809 `attributes` carried only interpretation evidence; since #809 it carries the dependency set that admission and withholding follow, so the omission is now load-bearing. The migration is operator-authorized (structural lifecycle), so this is not an unauthenticated-caller channel; it is a governance-laundering gap of exactly the kind the module says it prevents. Prior D(i) cited `checkpoint_migration.py:716` as protecting the field but did not observe that the new field is unprotected.
- **Graphiti substrate NOTE:** `graphiti_driver.write_fact` (125-139) persists `episode_uuids` but not `attributes`, and `_to_fact` (223-236) constructs `Fact` without `attributes`. On that substrate every fact reads back as a legacy fact: `_derivation_refs` falls back to `episode_uuids` for *new* writes too, so #809 is silently inert there (as are `write_provenance` and `write_semantics`). The driver is a declared probe, not the qualified production substrate, but it implements the port; if it is ever used behind the facade the F-R3-2 oracle is fully open for new writes with no indication.

## 3. Legacy-store analysis (facts persisted without `attributes["canonical_derivation"]`)

Which F-R3-2 channels stay open, for whom:
- (L1) Writer `W` of legacy fact `R` citing foreign `d` (or a guessed id): when `d`'s generation is pruned or permanently deleted, `R` is refused `derived_from_tombstoned_source` (1432) and `derived_from_deleted_logical_memory` (2013) for every reader; `W`'s `recall` hides `R` (hidden set, 1090), `write_semantics(R)` is `None` (976), and `history(M_R)` flips from a live record to `{None, 0, tombstoned: False}` (1267-1274). `W` observes `d`'s deletion. Open exactly as before #809.
- (L2) Forward guesses: a legacy `R` citing not-yet-minted ids `G1..Gn` (identifiers are sequential) binds each `Gk` the moment it is minted in *any* scope, through the fallback; `R` then flips on `Gk`'s deletion. A single legacy row is a standing canary over future deletions tenant-wide, not only over facts that existed when it was written. Prior D(ii) stated the backward case only.
- (L3) Transitive propagation into NEW writes: a post-#809 fact `N` whose writer is eligible for legacy `R` and cites it binds `R` (correctly); `_derives_from_deleted` then walks `_derivation_refs(R)` = `episode_uuids` (2053), so `N` is withheld when foreign `d` is deleted, although `N`'s writer could never read `d` and `N`'s own record is clean. The residual is therefore not confined to legacy rows: any new chain rooted in a legacy row inherits the tenant-wide taint. This is a direct consequence of the owner's "no silent release" choice and is correct under it, but it means "sound for new writes" holds only for chains with no legacy ancestor.
- (L4) `undeclared_residue` of a legacy citer still lists it to the deleter (fallback at 2273); same as before.
- (L5) Co-holders of a legacy shared fact see it vanish with the citer (H7 propagation); same as before.
